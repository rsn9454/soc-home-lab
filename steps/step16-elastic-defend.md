# Step 16 — Install and Test Elastic Defend (EDR)

## Objective
Add Elastic Defend — Elastic's built-in Endpoint Detection and Response (EDR) solution — to the Windows target via Fleet, confirm the endpoint appears in Kibana Security, then re-execute the Apollo agent to verify that Elastic Defend blocks and quarantines the payload automatically.

---

## Prerequisites
- Windows Server 2022 VM2 is enrolled in the `windows-endpoints` Fleet policy with a healthy Elastic Agent
- Apollo agent payload (`apollo.exe`) is still present on the Desktop of VM2, or can be re-transferred
- The Apollo detection rule is active in Kibana Security
- VM1 (ELK + Fleet) is running
- VM2 (Windows target) is booted and logged in as Administrator


---

## What is Elastic Defend

Elastic Defend is Elastic's native EDR integration. It runs alongside the Elastic Agent on the endpoint and adds active prevention capabilities on top of the passive telemetry that Sysmon and Windows Event Logs provide.

| Capability | Sysmon | Elastic Defend |
|---|---|---|
| Process creation logging | ✅ | ✅ |
| Network connection logging | ✅ | ✅ |
| Malware **detection** | ❌ | ✅ |
| Malware **prevention** | ❌ | ✅ |
| File **quarantine** | ❌ | ✅ |
| Remote endpoint **isolation** | ❌ | Paid licence only |
| Ransomware protection | ❌ | ✅ |

The key difference: Sysmon observes and logs — Elastic Defend observes, logs, **and stops**. This step demonstrates what defence-in-depth looks like: the SIEM detects (Kibana alert), the EDR prevents (Elastic Defend blocks execution).

## Step 1 — Add Elastic Defend integration in Kibana

1. Go to **Management → Integrations**
2. Search for **Elastic Defend**
3. Click **Elastic Defend** → **Add Elastic Defend**

### Configure the integration

| Setting | Value |
|---|---|
| Integration name | `Elastic Defend - Windows` |
| Description | `EDR protection for Windows target VM2` |
| Configuration | Endpoint Security (recommended) |
| Where to add | Existing hosts |
| Existing agent policy | `windows-endpoints` |

### Configuration settings
Click **Show advanced settings** and confirm:

| Setting | Value |
|---|---|
| Malware protection | **Detect & Prevent** |
| Ransomware protection | **Detect & Prevent** |
| Memory threat protection | **Detect & Prevent** |
| Malicious behaviour protection | **Detect & Prevent** |
| Attack surface reduction | Enabled |

Click **Save and deploy changes**.

The Elastic Agent on VM2 will receive the updated policy within 30 seconds and Elastic Defend will initialise on the endpoint.

## Step 3 — Re-enable Windows Defender (important)

Windows Defender was disabled to allow the Apollo payload to run. Before testing Elastic Defend, re-enable Defender to simulate a clean state — then Elastic Defend will be the active protection layer.

1. Go to **Windows Security → Virus & threat protection → Manage settings**
2. Toggle **Real-time protection** → **On**

> With Elastic Defend now installed, both Defender and Elastic Defend are active. In production, Elastic Defend typically replaces Defender as the primary endpoint protection — but for this test, having both active is fine. Elastic Defend will intercept the payload first.

---

## Step 4 — Re-execute the Apollo agent and observe the block

With Elastic Defend active, attempt to run the Apollo payload again.

### Expected behaviour

Instead of executing and beaconing, Elastic Defend should:

1. **Block** the execution immediately
2. **Quarantine** the file (move it out of the accessible filesystem)
3. **Generate a Kibana alert** under Security → Alerts

A Windows notification may appear: "Elastic Security prevented a malicious action" or similar.

### Verify the block in Kibana

Go to **Security → Alerts** — a new alert should appear within seconds:

| Field | Expected value |
|---|---|
| Rule | Elastic Endpoint Security (auto-generated by Elastic Defend) |
| Severity | Critical or High |
| Event type | Malware prevention event |
| File | apollo.exe |
| Action taken | Quarantined |
| Agent | WIN-KT9TVSF1T0C |

## Remote isolation — what it does in production

On a paid Elastic licence, the **Isolate** button on the Endpoint detail page cuts the endpoint from the network while keeping the Elastic Agent connection alive. This means:

- The compromised host can no longer communicate with the C2 server
- The analyst can still collect forensic data via the agent
- The endpoint cannot be used for lateral movement
- Isolation can be lifted remotely once remediation is complete

## Key takeaway
Before this step, the Apollo agent executed freely because the only protection layer (Windows Defender) had been deliberately disabled. Now, Elastic Defend blocked the payload before it could even start — the C2 beacon was never established, and no Sysmon Event ID 3 was ever generated. This is the practical demonstration of why modern endpoint security has shifted from signature-based antivirus toward behaviour-based EDR: Elastic Defend did not need to know about the Apollo agent specifically to block it — it recognised the behaviour as malicious. In a layered security architecture, the SIEM (Kibana + detection rules) handles detection and investigation, while the EDR (Elastic Defend) handles active prevention — two different tools doing two complementary jobs.
